# Starting a project, a first slice, a prototype or an estimate

You will already propose a thin end-to-end slice shown to the user early. Keep that. These are the
parts usually left out.

**18. Run the requirements loop inside the sitting, and ration the user's attention.** (Requirements
are learned in a feedback loop, Topic 45: *bends*; users are part of the team, Topic 47:
*strengthens*.) Seeing used to be expensive to arrange, so the loop ran once an iteration. An agent can
change a working mockup while the user watches. Book the user for a working session, change it in
front of them, and write what they say as examples. When code takes minutes, the wait for someone who
knows the domain is the schedule, so spend their hours on purpose.
*Pitfall:* scope creep. When each addition costs almost nothing to build, a visible list of requests is
weak control. Say what each addition costs to verify and to keep.

**19. Decide out loud which code is kept and which is thrown away.** (Tracer code is not a prototype,
Topic 12: *bends*; prototype to learn, Topic 13: *strengthens*; prototype mistaken for product:
*strengthens*.) The tracer slice is production code: it gets the contracts, the tests and the review,
because it is the skeleton every later agent session will copy. A prototype answers one question and
is deleted. An agent-built demo looks finished in an afternoon, so say before you show it that it is
not the product, and delete it afterwards. Choosing the riskiest thing to trace first is still the
engineer's call.

On estimates: give a range, estimate from a model in which the expensive term is checking the code,
and let the first iterations set the schedule (Topic 15: *bends* and *strengthens*). No past project
predicts an agent-built one. On method: pilot an agent practice small and keep what works for you;
copying another team's agent set-up without their discipline is a cargo cult (Topic 50: *holds*).
